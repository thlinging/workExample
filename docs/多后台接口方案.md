# 前端同时对接两个后台的方案（axios + nginx）

> 背景：现在只有一个接口前缀 `api`，生产环境由 nginx 反代。需求是同一个前端同时请求两个后台服务。
>
> 本仓库现状：尚未引入 axios，`vue.config.js` 里也没有 `devServer.proxy`（只有主题相关配置）。以下按"从零引入"编写，已有项目照搬时只需把 A 服务对应到现有的 `/api`。

---

## 结论先说

**用「多前缀 + 多 axios 实例」**：给第二个后台再分配一个路径前缀（如 `/api` 与 `/bapi`），开发期用 `devServer.proxy` 分流，生产期用 nginx 两个 `location` 分流。前端保持同域同源，不需要 CORS、不需要处理跨域 Cookie，nginx 只多一段配置。

只有当后台数量会长到 3 个以上、或部署时后端地址要由运维随时改，才升级到方案 B / 方案 C。

| 方案 | 适用 | 代价 |
|---|---|---|
| **A. 多前缀 + 多实例**（推荐） | 2~3 个后台，前缀固定 | 每加一个后台改一次 nginx + 重新打包 |
| B. 单实例 + 服务标记 | 后台 3+，想集中管理 | 多一层 url 改写逻辑 |
| C. 运行时配置文件 | 一次打包多环境部署 | 多一个 `public/config.js`，首屏需先加载 |
| ~~D. 直接写绝对域名~~ | 不推荐 | CORS、Cookie 跨域、换环境要重新打包 |

---

## 方案 A：多前缀 + 多 axios 实例

### 1. 环境变量定义前缀

`.env.development`：

```bash
# A 服务（原有）
VUE_APP_BASE_API=/api
# B 服务（新增）
VUE_APP_BASE_API_B=/bapi
```

`.env.production`：

```bash
VUE_APP_BASE_API=/api
VUE_APP_BASE_API_B=/bapi
```

生产和开发前缀保持**完全一致**，是这个方案的关键——这样"本地能跑、线上 404"的问题只可能出在 nginx 上，排查面小。

> 注意 vue-cli 只会把 `VUE_APP_` 开头的变量注入到客户端代码。

### 2. 请求工厂：一份拦截器，产出多个实例

`src/utils/request.js`

```js
import axios from 'axios'
import { message } from 'ant-design-vue'

// 两个后台的差异只在 baseURL 和取 token 的方式上，其余（错误提示、
// 响应解包、超时）完全共用，所以抽成工厂而不是复制两份配置。
function createRequest (options = {}) {
  const instance = axios.create({
    baseURL: options.baseURL,
    timeout: options.timeout || 15000
  })

  instance.interceptors.request.use(config => {
    const token = options.getToken && options.getToken()
    if (token) config.headers[options.tokenHeader || 'Authorization'] = token
    return config
  })

  instance.interceptors.response.use(
    res => {
      const body = res.data
      // 两个后台若返回结构不同，用 options.unwrap 各自覆盖
      return options.unwrap ? options.unwrap(body) : body
    },
    err => {
      // 带上服务名，两个后台同时挂的时候能一眼看出是谁
      message.error(`[${options.name}] ${err.message}`)
      return Promise.reject(err)
    }
  )

  return instance
}

export default createRequest
```

`src/utils/http.js`

```js
import createRequest from './request'

export const requestA = createRequest({
  name: 'A服务',
  baseURL: process.env.VUE_APP_BASE_API,
  getToken: () => localStorage.getItem('token')
})

export const requestB = createRequest({
  name: 'B服务',
  baseURL: process.env.VUE_APP_BASE_API_B,
  // B 后台常见的是另一套鉴权，独立取
  getToken: () => localStorage.getItem('token_b'),
  tokenHeader: 'X-Access-Token'
})
```

### 3. api 层按服务分目录

```
src/api/
  a/            # A 服务
    user.js
    order.js
  b/            # B 服务
    report.js
```

`src/api/b/report.js`

```js
import { requestB } from '@/utils/http'

export function getReportList (params) {
  return requestB.get('/report/list', { params })
}
```

业务组件里只 `import { getReportList } from '@/api/b/report'`，**不感知**它走的是哪个后台。将来 B 服务并入 A，只改这一个文件的 import。

### 4. 开发期代理

`vue.config.js` 的 `devServer` 里加：

```js
devServer: {
  host: '0.0.0.0',
  port: 8080,
  open: true,
  overlay: { warnings: false, errors: true },
  proxy: {
    '/api': {
      target: 'http://192.168.1.10:8080',
      changeOrigin: true
      // 后端本身带 /api 上下文，所以不 rewrite；见下方「前缀剥离」
    },
    '/bapi': {
      target: 'http://192.168.1.20:9090',
      changeOrigin: true,
      pathRewrite: { '^/bapi': '' }
    }
  }
}
```

⚠️ 代理规则按对象 key 顺序匹配，**长前缀写在前面**。若前缀是 `/api` 和 `/api-b` 这种包含关系，`/api` 写在前会把 `/api-b` 的请求也吃掉。用 `/api` + `/bapi` 这种不互为前缀的命名可以彻底规避。

### 5. 生产 nginx

```nginx
server {
    listen 80;
    server_name your.domain.com;

    root /usr/share/nginx/html;
    index index.html;

    # 前端 SPA
    location / {
        try_files $uri $uri/ /index.html;
    }

    # A 服务：保留 /api 前缀转发（后端 context-path 是 /api）
    location /api/ {
        proxy_pass http://192.168.1.10:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # B 服务：剥掉 /bapi 前缀转发（后端根路径直接是业务路由）
    location /bapi/ {
        proxy_pass http://192.168.1.20:9090/;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

---

## ⚠️ 最大的坑：前缀剥离要和 devServer 对齐

`proxy_pass` 的**末尾斜杠**决定前缀是否被剥掉，这是线上 404 的头号原因：

| nginx 写法 | 请求 `/bapi/report/list` 实际打到后端的路径 | 对应 devServer |
|---|---|---|
| `proxy_pass http://host:9090;`（无斜杠） | `/bapi/report/list` | 不写 `pathRewrite` |
| `proxy_pass http://host:9090/;`（有斜杠） | `/report/list` | `pathRewrite: { '^/bapi': '' }` |

**判断依据**：后端接口的真实路径带不带这个前缀。
- 后端是 Spring Boot 且配了 `server.servlet.context-path=/api` → 前缀是后端的一部分，**不剥**。
- 后端根路径直接就是 `/report/list`，前缀纯粹是前端为了给 nginx 分流造出来的 → **要剥**。

同一个服务，devServer 的 `pathRewrite` 和 nginx 的尾斜杠必须做同一件事，否则本地正常线上全挂。

### 其他 nginx 注意点

- `location /api/`（带尾斜杠）比 `location /api` 安全：后者会匹配到 `/apixxx` 这种意外路径。
- nginx 是**最长前缀优先**，不是配置顺序优先，所以 `/api` 和 `/api-b` 在 nginx 侧不会冲突——但 devServer 侧会。为了两边行为一致，还是用不互为前缀的命名。
- 文件上传要加 `client_max_body_size 50m;`。
- 长轮询 / 导出大文件要加 `proxy_read_timeout 300s;`。
- 如果 B 服务有 SSE 或 WebSocket，需额外 `proxy_http_version 1.1;` + `proxy_set_header Upgrade $http_upgrade;` + `Connection "upgrade";`，并关闭 `proxy_buffering`。

## 方案 B：单实例 + 服务标记（后台 3+ 时）

不为每个后台建实例，而是在请求拦截器里按标记改写 baseURL：

```js
// src/utils/http.js
const SERVICES = {
  a: process.env.VUE_APP_BASE_API,      // /api
  b: process.env.VUE_APP_BASE_API_B,    // /bapi
  file: process.env.VUE_APP_BASE_API_FILE
}

const request = axios.create({ timeout: 15000 })

request.interceptors.request.use(config => {
  // config.service 由调用方传入，默认走 a
  config.baseURL = SERVICES[config.service || 'a']
  return config
})
```

调用：

```js
export function getReportList (params) {
  return request.get('/report/list', { params, service: 'b' })
}
```

优点是新增后台只改 `SERVICES` 一处；缺点是拦截器无法再按服务定制（token header、响应解包结构），如果各后台返回体差异大，还是方案 A 更清晰。

## 方案 C：运行时配置（一次打包，多环境部署）

前缀写死在 `.env` 意味着换环境要重新 `npm run build`。若同一个包要发给多个客户/多套环境，把地址挪到运行时：

`public/config.js`（**不参与打包**，构建后原样复制到 dist，运维可直接改）：

```js
window.__APP_CONFIG__ = {
  BASE_API: '/api',
  BASE_API_B: '/bapi'
}
```

`public/index.html` 的 `<head>` 里最先引入：

```html
<script src="<%= BASE_URL %>config.js?v=<%= Date.now() %>"></script>
```

> 加时间戳查询参数，避免 nginx / 浏览器缓存住旧配置——改了配置刷新不生效是这个方案的典型问题。也可以在 nginx 里对 `config.js` 单独设 `add_header Cache-Control "no-cache";`。

`src/utils/http.js` 里取值时兜底：

```js
const CONF = window.__APP_CONFIG__ || {}
const baseA = CONF.BASE_API || process.env.VUE_APP_BASE_API
const baseB = CONF.BASE_API_B || process.env.VUE_APP_BASE_API_B
```

这个方案和方案 A 不冲突，可以叠加使用。

## 为什么不推荐直接写绝对域名

```js
// ❌
axios.create({ baseURL: 'http://192.168.1.20:9090' })
```

代价：

1. **跨域**。要么后端开 CORS（预检请求让每个接口多一次 OPTIONS 往返），要么根本调不通。
2. **Cookie 传不过去**。跨域要 `withCredentials: true` + 后端 `Access-Control-Allow-Credentials` + 不能用 `Allow-Origin: *`；如果是 HTTPS 页面还要 `SameSite=None; Secure`。
3. **混合内容**。前端 HTTPS、后端 HTTP 会被浏览器直接拦截。
4. **换环境要重新打包**，且后端 IP 暴露在前端产物里。

走 nginx 同域反代把这四条全部消掉，这正是"真实环境是 nginx"时最该利用的优势。

## 落地检查清单

- [ ] 确认 B 后台接口真实路径是否带前缀 → 决定 devServer `pathRewrite` 与 nginx 尾斜杠
- [ ] 两个前缀不互为前缀（推荐 `/api` + `/bapi`）
- [ ] 两个后台的鉴权是同一套 token 还是各自一套 → 决定用方案 A 还是 B
- [ ] 两个后台的响应体结构（`code`/`data`/`msg` 字段名）是否一致 → 不一致就在各自 `unwrap` 里对齐，别让业务层感知
- [ ] api 层按服务分目录，业务组件不感知后台归属
- [ ] nginx 配好后 `nginx -t` 校验再 `nginx -s reload`
- [ ] 上传/导出接口确认 `client_max_body_size` 和 `proxy_read_timeout`
