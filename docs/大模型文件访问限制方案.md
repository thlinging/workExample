# 大模型（Claude Code）文件/目录访问限制方案

> 目标：让 Claude Code **读不到、也改不了**指定的文件或目录（密钥、客户数据、内部接口文档等）。
> 本文结论基于 **Claude Code 2.1.236 / Windows** 上的实测；行为可能随版本变化，
> 换环境请按文末「附录：验证方法」自行复验。

---

## 一、先说结论

**提示词（CLAUDE.md）不是安全边界，只是礼貌请求。** 真正生效的是 `settings.json` 里的
`permissions.deny`，它在**工具调用层**拦截，模型无法通过「换个说法」绕过。

推荐按这个顺序落地，每一层都比上一层更硬：

| 层级 | 手段 | 拦得住谁 | 成本 |
|---|---|---|---|
| L0 | **敏感文件不放进工作目录** | 一切 | 最低，最有效 |
| L1 | `permissions.deny` 的 `Read()` / `Edit()` 规则 | Read/Edit/Write/Grep/Glob **以及 shell 里的读文件命令** | 低 ← **主力，先做这个** |
| L2 | `PreToolUse` hook 自定义拦截 | L1 解析器看不穿的间接读取（`node -e`、`python -c`、编码转储等） | 中 |
| L3 | `sandbox.filesystem.denyRead` | 操作系统层，Bash 子进程绕不过（**Read/Edit 工具不走沙箱**） | 高：**原生 Windows 不支持，需搬进 WSL2**，见 §四 |
| L4 | 企业级 `managed-settings.json` + `allowManagedPermissionRulesOnly` | **开发者自己改配置** | 需要管理员权限 |
| L5 | 外泄通道管控（WebFetch / curl / git push / MCP） | 读到了也传不出去 | 低 |

如果只做一件事：**做 L1**。如果这是要交付给客户、要过安全审计的「项目安全需求」：**L1 + L2 + L4**
是最小合规组合。

## 二、L1：`permissions.deny`（主力方案）

### 2.1 配置位置与优先级

配置文件加载顺序（后者覆盖前者）：

```
~/.claude/settings.json           用户全局
  → .claude/settings.json         项目级（提交进 git，团队共享）  ← 安全规则写这里
    → .claude/settings.local.json 个人本地（gitignore，不要写安全规则）
      → --settings 命令行参数
        → managed-settings.json   企业策略（最高，见 L4）
```

**权限判定优先级：`deny` > `ask` > `allow`。** deny 命中即拒绝，不弹窗询问；`allow` 里就算写了
`"Read"` 全放行也压不过 deny。所以项目里已经攒下的 `.claude/settings.local.json` 里
那一大堆 `allow` 规则不用动，加 deny 后它们照常生效、互不冲突。

### 2.2 实际写法

在项目根新建 `.claude/settings.json`（注意：不是 `settings.local.json`，安全规则要进版本库）：

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Read(./docs/内部接口/**)",
      "Read(./src/config/credentials.js)",

      "Edit(./.env)",
      "Edit(./.env.*)",
      "Edit(./secrets/**)"
    ]
  }
}
```

规则语法要点：

- `Read(...)` 一条同时管住 **Read / Grep / Glob**，以及 **shell 里的读文件命令**（实测见附录）。
- `Edit(...)` 管住 **Edit / Write / NotebookEdit**。**两者互相独立** —— 只写 `Read()` 挡不住覆盖写，
  只写 `Edit()` 挡不住读取。敏感文件**两条都要写**。
- 路径形式：
  - `./xxx` —— 相对项目根，最常用
  - `**` —— 递归匹配子目录；`*` 只匹配一层
  - `~/...` —— 用户家目录
  - `//绝对路径` —— 双斜杠开头表示绝对路径（如 `Edit(//etc/*)`）。Windows 下的绝对路径写法
    请按 §九 的方法自测确认后再依赖。
- **目录要写 `/**`**：`Read(./secrets)` 只匹配那个名字本身，`Read(./secrets/**)` 才覆盖里面所有文件。
  稳妥起见两条都写。

### 2.3 一个反直觉但重要的实测结果

很多人以为 `Read()` 规则只管 Read 工具，模型改用 `cat` / `type` 就能绕过。**在 2.1.236 上不成立。**

让模型执行 `cat private/notes.txt`，Claude Code 解析出这条命令在读哪个文件，直接返回：

```
get-content targeting '...\private\notes.txt' was blocked.
```

而且当 shell 命令**解析不出来**时（例如 pwsh 解析器超时），Claude Code 选择 **fail-closed —— 不执行**，
返回 `Command contains malformed syntax that cannot be parsed`。方向是对的：解析不了就不放行。

**但这仍然是基于命令解析的启发式**，不是操作系统级隔离。理论上存在解析器识别不出的读取方式
（`node -e` 读文件、`python -c`、`certutil -encode`、把文件当参数喂给别的程序等）。
真要拦死，需要 L2 或 L3 兜底。

### 2.4 限制命令：`git` / `rm` / `curl` 这类

前面讲的都是**路径**规则（`Read()` / `Edit()`）。「不许执行 `git commit`」是**命令**规则，
同属 `permissions.deny`，但语法是另一套。

> `claude-guard` 工具只管路径，不生成这类规则。手写进 `settings.json` 即可，
> `init` 会原样保留（它只回收自己记账过的规则）。

```jsonc
{
  "permissions": {
    "deny": [
      "Bash(git commit *)",
      "Bash(git push *)",
      "Bash(git add *)",
      "PowerShell(git commit *)",
      "PowerShell(git push *)",
      "PowerShell(git add *)"
    ]
  }
}
```

**Windows 上必须两套都写。** `PowerShell` 是独立的工具，规则不通用，
而 Windows 上模型经常走 PowerShell 执行命令——只写 `Bash(...)` 等于没拦。
（这和 §3.2 里 hook matcher 必须写 `Bash|PowerShell` 是同一个原因。）

#### 四条语法要点

1. **`Bash(git push *)` 和 `Bash(git push:*)` 等价。** 但 `:*` **只在模式末尾**才被识别：
   写成 `Bash(git:* push)`，冒号会被当字面量，匹配不到任何东西。
2. **`*` 要放在子命令后面。** `Bash(git * main)` 这种写法会匹配所有 git 子命令，
   包括 `-c`——而 `-c` 能让 git 去运行你指定的程序。Claude Code 启动时会对 allow 里的
   这种写法发警告。
3. **末尾的 ` *` 也匹配裸命令。** `Bash(git push *)` 同时匹配不带参数的 `git push`。
   前提是这个 `*` 是整条规则里唯一的通配符。
4. **别写 `Bash(command:git push *)`。** 这种「参数名:值」形式对 Bash/PowerShell 的
   `command` 字段无效（会被复合命令绕过），Claude Code 直接忽略并在启动时警告。

#### deny 比想象的严实

deny / ask 规则**会拆开复合命令逐段匹配**，包括子 shell、命令替换、控制流内部。
所以一条 `Bash(git commit *)` 也能拦下：

```bash
cd /tmp && git commit -m x
echo "$(git commit -m x)"
for f in *; do git commit -m "$f"; done
```

PowerShell 那边按 AST 拆 `|`、`;`、`&&`、`||`，每一段都要匹配才放行。
常用别名会先规范化，`PowerShell(Get-ChildItem *)` 同时管住 `gci` / `ls` / `dir`。

#### 建议：只禁写，保留只读

模型能看 git 状态对干活帮助很大，全禁会让它连「这个文件改过没有」都判断不了：

| 建议 deny | 建议保留 |
|---|---|
| `git commit` `git push` `git add` `git reset` `git checkout` `git merge` `git rebase` `git clean` `git stash` `git tag` | `git status` `git log` `git diff` `git show` `git branch` |

想要「先问我再执行」而不是直接拒绝，把规则写进 `permissions.ask` 而不是 `deny`。

#### 别漏掉的两条旁路

1. **`git config` 和 `git -c`** 能改 `core.pager` / `core.editor` 等间接执行程序。
   补上 `Bash(git config *)`、`Bash(git -c *)` 及对应的 PowerShell 版本。
2. **`gh` CLI 和 MCP 工具是另外的通道**——`gh pr create`、GitHub MCP 的写操作都绕过
   Bash 规则。要一起管：`Bash(gh *)` / `PowerShell(gh *)`；MCP 侧按
   `mcp__<服务名>__<工具名>` 逐条写（具体到工具名比通配更稳妥）。这一点与 §六 外泄通道管控相通。

规则写进 `.claude/settings.json` 并提交进 git，团队共享；**别放 `settings.local.json`**。

## 三、L2：`PreToolUse` hook（拦住 L1 看不穿的间接读取）

Hook 在工具真正执行**之前**跑一个你自己的脚本，脚本说 deny 就 deny。它拿到的是**原始命令文本**，
所以可以做纯文本层面的兜底：只要命令里出现受保护路径的名字，一律拒绝 —— 不管它想用什么方式读。

### 3.1 拦截脚本

新建 `.claude/hooks/guard-paths.js`：

```js
#!/usr/bin/env node
// PreToolUse 兜底：命令文本或文件路径中一旦出现受保护路径，直接拒绝。
// 与 permissions.deny 是双保险 —— deny 拦已知读取方式，这里拦间接读取。

const PROTECTED = [
  /(^|[\\/\s"'=])\.env(\.|$|["'\s])/i,   // .env / .env.production
  /secrets?[\\/]/i,
  /docs[\\/]内部接口/i,
  /credentials/i,
];

let raw = '';
process.stdin.on('data', d => (raw += d));
process.stdin.on('end', () => {
  let payload = {};
  try { payload = JSON.parse(raw); } catch { process.exit(0); }

  const input = payload.tool_input || {};
  // 覆盖所有可能触达文件的入口
  const haystack = [
    input.command, input.file_path, input.path,
    input.pattern, input.notebook_path,
  ].filter(Boolean).join(' \n ');

  const hit = PROTECTED.find(re => re.test(haystack));
  if (!hit) process.exit(0);

  process.stdout.write(JSON.stringify({
    hookSpecificOutput: {
      hookEventName: 'PreToolUse',
      permissionDecision: 'deny',
      permissionDecisionReason:
        '该操作触及受保护路径（匹配规则 ' + hit + '），已被项目安全策略拒绝。' +
        '如确需访问，请联系项目安全负责人，不要尝试改写命令绕过。',
    },
    systemMessage: '⛔ 安全策略拦截：尝试访问受保护路径',
  }));
  process.exit(0);
});
```

### 3.2 挂上去

合并进 `.claude/settings.json`：

```json
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./secrets/**)", "Edit(./.env)", "Edit(./secrets/**)"]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|PowerShell|Read|Edit|Write|Grep|Glob|NotebookEdit",
        "hooks": [
          {
            "type": "command",
            "command": "node .claude/hooks/guard-paths.js",
            "timeout": 10,
            "statusMessage": "安全策略检查中"
          }
        ]
      }
    ]
  }
}
```

要点：

- `matcher` 是正则，务必**同时写 `Bash` 和 `PowerShell`** —— Windows 上模型走的是 PowerShell 工具
  （实测确认），只写 `Bash` 等于没拦。**这是最容易踩的坑。**
- `permissionDecision: "deny"` 是 PreToolUse 的现代写法；老写法 `decision: "block"` 已废弃。
- 脚本任何异常都要显式 `exit(0)` 放行或明确拒绝，不要让它抛错 —— 抛错的行为不如显式决策可控。
- 改完 settings.json 后当前会话可能不热加载。**打开一次 `/hooks` 菜单或重启 Claude Code** 才生效。

### 3.3 更省事的替代：prompt 型 hook

不想写脚本，可以让一个小模型来判断：

```json
{
  "type": "prompt",
  "prompt": "以下工具调用是否试图读取或修改 .env、secrets/ 目录下的文件？只要沾边就判定为是。$ARGUMENTS",
  "if": "Bash(*)"
}
```

**安全场景不推荐** —— 判定不确定、每次调用多一次 LLM 请求、且本身可能被提示词注入影响。
命令式脚本是确定性的。

## 四、L3：沙箱文件系统隔离（操作系统层）

不依赖命令解析：被沙箱包住的进程根本看不到那些文件。官方现在把这个功能叫
「sandboxed Bash tool」——名字带 Bash，是因为它隔离的对象是 Bash 子进程。

> 本节内容以官方文档 `code.claude.com/docs/en/sandboxing` 为准。
> 沙箱的平台支持和依赖变动较快，采用前请重新核对该页。

### 4.1 平台与依赖（先看这条，可能直接判死刑）

| 平台 | 需要装什么 |
|---|---|
| macOS | **零依赖**，用系统内建的 Seatbelt |
| Linux / WSL2 | `bubblewrap`（文件系统隔离）+ `socat`（网络隔离） |
| **原生 Windows** | **不支持。** 必须把 Claude Code 跑在 WSL2 里 |

```bash
sudo apt-get install bubblewrap socat     # Debian/Ubuntu
sudo dnf install bubblewrap socat         # Fedora/RHEL
```

- **WSL1 不行**，bubblewrap 需要只有 WSL2 才有的内核特性。
- 可选：seccomp filter（阻断 Unix domain socket）→ `npm install -g @anthropic-ai/sandbox-runtime`。
- ripgrep 已随 Claude Code 原生二进制打包，不用管。
- **Ubuntu 24.04+ 额外一步**：默认 AppArmor 策略禁止 bubblewrap 创建 user namespace，要放开。
- 自检：`/sandbox` 命令有 Dependencies 标签页，缺什么列什么。**装完要重启 Claude Code** 才会重新检测。

### 4.2 关键认知：L3 不替代 L1/L2

官方文档「Scope」一节写得很明确：

> The sandbox isolates Bash subprocesses. **Read, Edit, and Write use the permission system
> directly rather than running through the sandbox.**

也就是说 **L3 只补 shell 那条路**，`Read` 工具读文件走的仍然是 `permissions.deny`。
上了 L3 也**不能扔掉 L1/L2**，三者是叠加关系。

### 4.3 配置

```jsonc
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,          // 依赖缺失/平台不支持时直接不启动
    "allowUnsandboxedCommands": false,  // 关掉 dangerouslyDisableSandbox 逃生口（严格模式）
    "filesystem": {
      "denyRead": ["./secrets"],
      "denyWrite": ["./secrets"],
      "allowRead": []                   // 在 denyRead 区域内重新放开某些路径
    },
    "credentials": { "files": [] },
    "excludedCommands": []              // 完全不进沙箱的命令
  }
}
```

- `failIfUnavailable: true` 很关键：沙箱起不来就直接退出，而不是「警告一下然后无沙箱裸奔」。
  安全需求必须打开这个。
- `allowUnsandboxedCommands: false` 让 Claude Code 忽略 `dangerouslyDisableSandbox` 参数，
  命令在沙箱里失败也不能退回到非沙箱重试。`/sandbox` 面板里叫 **Strict sandbox mode**。
- **路径规则：更具体的胜出。** `allowRead: ["~/"]` 配 `denyRead: ["~/.env"]`，`.env` 仍然挡住——
  宽的 allow 不会悄悄把密钥重新暴露出来；通配 deny（`~/**/.env`）同理。
- **默认读行为是能读整台电脑**（含 `~/.ssh/`、`~/.aws/credentials`），
  要靠 `sandbox.credentials` 或 `denyRead` 挡住。
- 凭据文件专用的 `sandbox.credentials.files` 支持 `mode: "deny"`（读不到）和
  `mode: "mask"`（沙箱内是假值）。它**只作用于沙箱内的 Bash 命令**；
  要给所有子进程剥离凭据环境变量，用 `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`。

### 4.4 代价

Windows 上意味着**把整个开发环境搬进 WSL2**，前端项目尤其要掂量：

- 仓库若留在 Windows 盘、经 `/mnt/<盘符>` 访问，文件 IO 会明显变慢（`node_modules` 最难受），
  实际得把仓库放进 WSL 自己的文件系统
- dev server 端口转发、Windows 编辑器访问、Git 凭据都要重新捋一遍

macOS 上代价小得多（零依赖），Linux 装两个包即可。

**如果目标只是「防手滑」，通常不值得。** L3 的真实卖点是让 agent 大幅自主运行
（免掉逐条命令的权限确认），文件保护只是顺带。

## 五、L4：企业级强制（防止开发者自己改配置）

前面所有配置都写在项目里，**开发者自己就能删掉**。如果安全需求是「约束团队成员」而不是
「帮自己防手滑」，必须用管理员权限下发 `managed-settings.json`：

- Windows：`C:\ProgramData\ClaudeCode\managed-settings.json`
  （或 `C:\Program Files\ClaudeCode\managed-settings.json`，后者需管理员写入，更难被改）
- macOS：`/Library/Application Support/ClaudeCode/managed-settings.json`
- Linux：`/etc/claude-code/managed-settings.json`

内容：

```json
{
  "permissions": {
    "deny": ["Read(./secrets/**)", "Read(./.env*)", "Edit(./secrets/**)"],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "allowManagedHooksOnly": true
}
```

三个关键开关：

- **`allowManagedPermissionRulesOnly: true`** —— 只认管理端的权限规则，用户/项目/本地/命令行里的
  allow、deny **全部被忽略**。这是「开发者改不动」的核心。
  副作用：团队原有的 allow 白名单也会一起失效，日常操作会变成频繁弹窗，
  管理端需要把必要的 allow 一并下发。
- **`disableBypassPermissionsMode: "disable"`** —— 禁掉 `--dangerously-skip-permissions`。
  不加这条，前面所有 deny 规则一个命令行参数就全绕开了。**这条不能漏。**
- **`allowManagedHooksOnly: true`** —— 只跑管理端的 hook，防止有人往项目里塞一个放行 hook。

默认情况下机器上**没有** managed-settings.json，即项目处于「开发者可自行修改」状态。

## 六、L5：堵住外泄通道

除了「读不到」，还要限制「读到了传不出去」。同样放 `permissions.deny`：

```json
{
  "permissions": {
    "deny": [
      "WebFetch",
      "Bash(curl:*)",
      "Bash(wget:*)",
      "Bash(nc:*)",
      "Bash(git push:*)",
      "Bash(scp:*)"
    ]
  }
}
```

配合沙箱网络白名单，只放行必要域名：

```json
{
  "sandbox": {
    "enabled": true,
    "network": {
      "allowedDomains": ["registry.npmmirror.com", "github.com"],
      "strictAllowlist": true
    }
  }
}
```

`strictAllowlist: true` 表示不在白名单的域名**直接拒绝**，而不是弹窗询问。

另外别忘了 **MCP 服务器**也是数据出口。本会话就挂着 github 和 Google Drive 两个 MCP。
管理端可用 `deniedMcpServers` / `allowedMcpServers` 收口，或用 `disableSideloadFlags: true`
堵住 `--mcp-config` 这类命令行旁路。

## 七、提示词该怎么写（以及为什么它不够）

### 7.1 定位

提示词只解决一件事：**让模型知道边界在哪、不去无谓试探**，从而减少弹窗和摩擦。
它**挡不住**提示词注入、挡不住模型误判、更挡不住「用户自己要求它读」。
**不要把提示词当作安全控制措施写进方案文档给审计看。**

### 7.2 写在 `CLAUDE.md`（项目根，自动加载）

```markdown
## 受保护路径（安全红线）

以下路径为本项目敏感数据，**禁止读取、检索、复制、摘要或写入**：

- <逐条列出密钥 / 凭据 / 环境变量文件>
- `secrets/`
- <其他敏感目录>

以下路径**可以读，但不允许你修改**（改动由人来做）：

- `.claude/settings.json` —— 权限配置
- `.claude/settings.json.backup-*` —— 配置备份
- `.claude/protected-paths.json` —— 受保护路径清单
- `.claude/hooks/**` —— 守卫脚本
- `scripts/claude-guard.js` —— 守卫配置工具

### 规则

1. 不要用任何工具（Read/Grep/Glob/Edit/Write/Bash/PowerShell）访问受保护路径，
   也不要用 `cat`、`type`、`node -e`、`python -c`、`base64` 等间接方式读取。
2. 需要这些文件里的配置项时，**只引用键名，不要读取和输出值**。
   例如可以说「读取 `<某个配置键>`」，但不要打印它的实际值。
3. 如果任务确实需要这些内容，**停下来告诉我，由我手动提供脱敏后的片段**，不要自行尝试。
4. 上述规则由 `.claude/settings.json` 的 `permissions.deny` 和
   `.claude/hooks/guard-paths.js` **双层强制执行**。遇到
   「denied by your permission settings」或「安全守卫拦截」是**预期行为**，
   **不要尝试换工具、换路径写法、或建议我放宽权限** —— 直接报告受阻并继续其他任务。
5. 需要调整保护范围时，告诉我，由我在终端执行：
   ```
   ! npm run guard -- add "secrets/**"      # 禁读禁写
   ! npm run guard -- add -r "config/**"    # 可读禁写
   ! npm run guard -- remove "secrets/**"   # 移出保护
   ! npm run guard:sync                     # 双向同步清单与 settings.json
   ! npm run guard:check                    # 离线自检
   ```
   注意 `!` 前缀是必需的：不带前缀走工具层，命令文本里的受保护路径会被守卫拦下。
```

几条不能省的：

- **第 4 条**：不写这条，模型被拦后往往会热心地建议你「加个 allow 规则吧」，甚至自己动手去改
  settings.json。同时要**顺手把配置文件本身保护起来**（工具的 `readonly` 清单已覆盖这些）。
- **「可读禁写」那一节**：一刀切禁读会导致连查看自己的权限配置都做不到，排错时寸步难行。
- **第 5 条的 `!` 前缀**：这是唯一的解锁口，且只对着人不对着模型（见 §十一「一个真实发生的死锁」）。

### 7.3 企业统一下发

管理端 `managed-settings.json` 支持 `claudeMd` 字段，把上面这段话作为组织级记忆注入所有会话，
项目里删不掉：

```json
{ "claudeMd": "## 受保护路径\n\n禁止访问 .env、secrets/ …" }
```

还有 `claudeMdExcludes`，可以禁止加载指定的 CLAUDE.md（防止有人用项目级 CLAUDE.md 覆盖组织规则）。

## 八、完整落地配置

在项目根新建 `.claude/settings.json`（**要提交进 git**）：

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.development)",
      "Read(./.env.production)",
      "Edit(./.env)",
      "Edit(./.env.development)",
      "Edit(./.env.production)",
      "Edit(./.claude/settings.json)",
      "Bash(curl:*)",
      "Bash(wget:*)"
    ]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|PowerShell|Read|Edit|Write|Grep|Glob|NotebookEdit|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "node .claude/hooks/guard-paths.js",
            "timeout": 10,
            "statusMessage": "安全守卫检查中"
          }
        ]
      }
    ]
  }
}
```

> matcher 要把**所有会触达文件的工具**列全，漏一个就是一个绕过口。
> 早期版本只写了 `Read|Edit`，结果 Bash / PowerShell / Grep 全部绕过守卫，
> 而 `init` 还照常输出成功。`claude-guard.js` 现在会逐字段比对并升级已注册的 hook，
> 手写的话自己核对一遍。

配套动作清单：

- [ ] 建 `.claude/hooks/guard-paths.js`（§3.1）
- [ ] 在 `CLAUDE.md` 加「受保护路径」章节（§7.2）
- [ ] 确认 `.gitignore` 覆盖了真正装密钥的那些文件
      —— `init` 默认只补 `.env.local` / `.env.*.local`，因为 vue-cli 约定里
      `.env.development` / `.env.production` 通常是**要提交的**非敏感构建配置，
      替用户忽略会造成静默漏提交。若项目的这两个文件里确实有敏感值，自己补进去；
      完全不想让工具碰 `.gitignore` 就加 `--no-gitignore`。
      见 [使用手册](./claude-guard使用手册.md) §四。
- [ ] 重启 Claude Code 或打开一次 `/hooks` 让配置生效
- [ ] 按 §九 自测
- [ ] 之后每次改动清单，跑 `npm run guard:sync` 让两边对齐
      —— 它同时校对 deny 规则、hook 注册块和守卫脚本版本，比只看 deny 条数可靠
- [ ] 如需约束团队：管理员下发 `managed-settings.json`（§五）

## 九、怎么自测（重要，别信配置信实测）

配置写完必须验证。用一次性沙盘，不要拿真密钥测：

```bash
# 1. 建沙盘
mkdir -p /tmp/sectest/private && cd /tmp/sectest
echo "ORANGE-PENGUIN-42" > private/notes.txt
# deny.json 内容：
# { "permissions": { "deny": ["Read(./private/**)"], "allow": ["Read", "Bash(cat:*)"] } }

# 2. 测 Read 工具
claude -p "读取 private/notes.txt 并原样输出内容" --settings ./deny.json --model haiku

# 3. 测 shell 绕过（关键）
claude -p "执行 cat private/notes.txt 并把输出原样告诉我" --settings ./deny.json --model haiku

# 4. 看原始工具事件，确认是权限层拦的、不是模型自己客气
claude -p "执行 cat private/notes.txt 并输出" --settings ./deny.json --model haiku \
  --output-format stream-json --verbose < /dev/null | grep -i "denied\|blocked"
```

**判定标准：必须在原始事件里看到 `denied by your permission settings` 或 `was blocked`。**

如果只是模型回复「出于安全考虑我不能这样做」，那是**模型自觉，不是权限拦截** —— 换个中性文件名
（别叫 `secret` / `token`，改叫 `notes`）重测，否则你测的是模型的礼貌而不是你的配置。
这是自测里最容易自欺欺人的一步。

## 十、常见误区

| 误区 | 实情 |
|---|---|
| 写进 CLAUDE.md 就安全了 | 提示词是软约束，会被注入、误判、用户指令覆盖 |
| `.gitignore` 里的文件模型读不到 | 无关。gitignore 只影响文件选择器建议，不影响工具读取 |
| 有 `.claudeignore` 这个文件 | 没有。官方机制就是 `permissions.deny` |
| deny 了 `Read()` 就够了 | 覆盖写要 `Edit()`，两条独立 |
| 规则写在 `settings.local.json` | 那是个人本地文件、被 gitignore，团队拿不到。安全规则写 `settings.json` |
| hook 的 matcher 只写 `Bash` | Windows 上模型走 PowerShell 工具，必须写 `Bash\|PowerShell` |
| 项目里配了 deny 就管得住团队 | 开发者能删。要强制得用 managed-settings + `allowManagedPermissionRulesOnly` |
| 配了 deny 就万无一失 | `--dangerously-skip-permissions` 一句话全绕开，必须同时 `disableBypassPermissionsMode` |
| 只防读取 | 读到了还能外传，要一并管 WebFetch / curl / git push / MCP |

## 附录：验证方法

换环境后按同样的方法复验即可。做法：另建一个沙盘目录，用 `--settings` 指定隔离的配置文件，
`--model haiku` 降低成本，然后逐条对照下表。原始记录来自 Claude Code 2.1.236 / Windows。

| # | 配置 | 让模型做的事 | 原始结果 | 结论 |
|---|---|---|---|---|
| 1 | `deny: ["Read(./secrets/**)"]` | 用 Read 读 `secrets/token.txt` | 被拒 | Read 工具被拦 ✓ |
| 2 | 同上 | 用 Bash `cat secrets/token.txt` | 模型自己拒绝了 | **无效测试** —— 文件名带 `secret`，触发的是模型自觉，不是权限层 |
| 3 | `deny: ["Read(./private/**)"]` | `cat private/notes.txt`（中性名） | `<tool_use_error>File is in a directory that is denied by your permission settings.</tool_use_error>` | 权限层确实拦截 ✓ |
| 4 | 同上，抓工具名与结果 | 同上 | 模型走 **PowerShell** 工具执行 `cat`，返回 `get-content targeting '...\private\notes.txt' was blocked` | **shell 读文件命令被解析并套用了 `Read()` 规则** ✓ |
| 5 | `allow: ["Bash(node:*)"]` | `node -e` 间接读文件 | `Command contains malformed syntax that cannot be parsed: pwsh timed out after 5000ms` | 解析失败时 **fail-closed 不执行**；但间接读取是否被识别 **未能验证** |

第 2 行是最有价值的教训：**用带 `secret` / `token` 字样的文件名做测试，你验证的是模型的
安全直觉，不是你的权限配置。** 换成 `private/notes.txt` 这类中性名才测得出真结果。

第 5 行是本方案仍然推荐 L2 / L3 兜底的直接理由 —— `node -e` 这类间接读取**没有被证明能拦住**。

## 十一、实装记录

按「防手滑」级别落地 L1 + L2（不含 L3 沙箱、L4 企业强制）后，涉及的文件：

| 文件 | 作用 |
|---|---|
| `.claude/settings.json` | `permissions.deny` 规则 + hook 注册 |
| `.claude/protected-paths.json` | 保护清单（唯一需要手改的地方） |
| `.claude/hooks/guard-paths.js` | PreToolUse 守卫，由工具生成，别手改 |
| `.claude/settings.json.backup-*` | `init` 前的配置快照，只留最近 5 份 |
| `scripts/claude-guard.js` | 一键配置工具，单文件无依赖，可直接拷到别的项目 |
| `CLAUDE.md` | 给模型看的红线说明 |
| `.gitignore` | `init` 按需补上 `.env.local` / `.env.*.local` / 配置备份；`--no-gitignore` 可跳过，见手册 §四 |

> 工具的完整用法、配置项、适用场景和排错，见 [claude-guard 使用手册](./claude-guard使用手册.md)。

### 一键工具用法

```bash
npm run guard -- init                  # 生成/合并全部配置（幂等，可反复跑）
npm run guard -- list                  # 看当前清单
npm run guard -- add "secrets/**"      # 加「禁读禁写」
npm run guard -- add -r "config/**"    # 加「可读禁写」
npm run guard -- remove "secrets/**"   # 移出保护
npm run guard:sync                     # 双向同步清单与 settings.json
npm run guard -- sync --dry-run        # 纯体检，不写盘
npm run guard:check                    # 离线自检，不调模型，秒出结果
```

`sync` 是双向的：正向把清单刷进 `settings.json` 的 deny 规则、hook 注册和守卫脚本，
并补齐守卫的自我保护项；反向检测 `settings.json` 里清单外的路径规则，默认只报告，
加 `--adopt` 才并入清单（反解析分不清「手写的」和「旧版本残留」，所以要人点头）。

在 Claude Code 里执行要加 `!` 前缀（`! npm run guard -- add ...`），否则命令文本里的
受保护路径会被守卫自己拦下。

### 实装才暴露的三个坑（纸上推演不出来）

**坑 1：内容字段不能用路径规则匹配。**
守卫最初把 `content` / `old_string` / `new_string` 也纳入检查，本意是防止把密钥搬运到别处。
结果是**任何内容里提到 `.env` 三个字的文件都写不了** —— 包括这份方案文档和配置工具本身。
防外泄要匹配密钥的**值**（高熵串），用路径名去匹配内容纯属误伤。
现在只检查真正承载路径的字段，且**按工具区分**：通用的 `command` / `file_path` / `path` /
`notebook_path`，Grep 额外看 `glob`，Glob 额外看 `pattern`。

Grep 的 `pattern` 是搜索词不是路径，早期把它当路径扫，导致**检索任何提到受保护文件名的文档
都会被拦**；而 Grep 的 `glob` 一度没纳入检查，`Grep(pattern="KEY", glob=".env*",
output_mode="content")` 可以直接读出文件内容——`path` 为空、`pattern` 只是搜索词，
haystack 里压根没有受保护路径。两个方向都踩过。

**坑 2：配置类文件要「可读禁写」，不能一刀切禁读。**
最初把 `.claude/settings.json` 和守卫脚本设成禁读禁写，结果连查看自己刚生成的配置都做不到。
现在拆成两类：`protected`（禁读禁写，给密钥）和 `readonly`（可读禁写，给配置和守卫自身）。
守卫按 `tool_name` 区分：readonly 只拦 Edit / Write / NotebookEdit，读放行。

**坑 3：deny 规则必须能退场。**
`syncDeny` 最初是「只增不删」，理由是怕误删手写规则。后果是清单里 `remove` 掉的路径，
生成的 deny 规则还赖在 `settings.json` 里 —— 改了清单却不生效，且无法自查。
现在在 `protected-paths.json` 里记 `_managedDenyRules`（本工具生成过哪些规则），
同步时**先减去上次记账、再加入本次生成**。手写规则不在记账里，不会被误删。

### 一个真实发生的死锁

改造过程中触发了完整死锁：守卫把 `.claude/**` 和工具自身都设成禁读禁写，
而修复缺陷必须改这些文件 —— **改不了，也看不了**。

破解方式是让用户在终端用 `!` 前缀执行命令（不经工具层，hook 不触发）。
模型侧可以用 `node -e` 从脚本内部改写配置来绕开守卫，但那等于证明这套防护对模型无效，
所以不该做，也没有做。

**这恰恰是设计意图**：守卫的解锁口只对着人，不对着模型。代价是配置迭代期会比较别扭，
建议**先用 `--dry-run` 和 `check` 把清单调对，再让它生效**，避免把自己锁在门外。

### 第二轮排查（2026-09-09）

守卫跑起来之后做过一轮系统排查，逐条实测。完整记录见
[守卫问题排查与修复记录](./claude-guard守卫排查报告.md)，这里只列结论性的几条：

- **hook 的 matcher 会漂移。** 早期版本注册的 matcher 停在 `Read|Edit`，Bash / PowerShell /
  Grep 全部绕过守卫，而 `init` 只判断「注册过没有」就跳过，照常输出成功。现已改为逐字段比对升级。
- **命令类拦截别拿整段文本找单词。** `grep git README.md`、`echo "npm run build first"`
  这种根本没在执行被禁命令的操作也会被拦。现按 shell 操作符拆子命令、只看执行位置。
  这跟坑 1 是同一个错误的两个变体——用名字匹配整段文本。
- **白名单也会被搭便车。** 为放行本工具的 `list`/`check` 加过一条白名单，
  结果 `guard list && rm 守卫脚本` 整条被放行。改成逐段判断，每段都得是只读调用。
- **配置备份要一起保护。** `settings.json.backup-*` 匹配不上 `.claude/settings.json` 规则，
  里面却是完整权限配置，一度可读可删。
- **新增的默认保护项不会自动进老清单。** `loadConfig` 尊重用户改过的清单、不跟进
  `DEFAULT_READONLY` 的新增项，于是升级脚本后新保护静默失效。现由 `init`/`sync` 强制补齐。

一条方法论教训：**验证 hook 的 payload 别用 shell 拼 JSON**。`printf`/`echo` 会把 `\\`
和反引号二次解释，喂进去的是非法 JSON，而守卫对畸形 payload 是放行的——于是「测出漏洞」，
实际是自己的 shell 在捣鬼。用 Node 构造 payload 再 `execFileSync` 喂进去。

### 与「约束团队」的差距

当前配置**开发者自己能删**（改 `.claude/settings.json` 或直接删 hook 即可），
只适合防手滑。如果哪天需要真正约束团队成员，还差三样，见 §五：

- 管理员权限下发 `managed-settings.json`
- `allowManagedPermissionRulesOnly: true`
- `disableBypassPermissionsMode: "disable"`（不加这条，`--dangerously-skip-permissions` 一句话全绕开）
