# 树节点编辑后跟随定位（tree-locator）

> 场景：懒加载的地区/组织树，节点悬浮出「编辑」，弹窗里能改名、也能换上级。
> 保存后要让这个节点重新回到用户视野里——哪怕它被挪到了一个从没展开过的分支下。
>
> **实现：`src/utils/tree-locator.js`**（纯 JS，不依赖 Vue，可直接拷进别的工程）
> 样式：`src/utils/tree-locator.scss` · 演示：`/easy-tree` 第三张卡片 · 假后端：`src/mock/orgTree.js`

一句话概括：**不刷整树，只动受影响的两个分支，然后逐级 load 把目标展开出来滚过去。**

---

## 一、为什么不能整树刷新

懒加载树的 `data` prop 基本不参与渲染（根节点来自 `load(node.level === 0)`），
所以"重新调接口刷新树"实际只能靠改 `:key` 重建组件——用户展开了七八层，全部清零。

而且就算是非懒加载的树，`watch.data` 里只调了 `store.setData`，
展开态、当前节点、滚动位置也一样全丢，`defaultExpandedKeys` 还不会自动重放。

代价远大于收益，所以走局部维护。

## 二、对外三个能力

```js
import { createTreeLocator } from '@/utils/tree-locator'

// 传 getter 而不是实例：树可能还没挂载、也可能被包在自己的封装组件里
const locator = createTreeLocator(() => this.$refs.orgTree)

// 1. 核心：把任意节点展开出来并滚进视野
await locator.locate(key, { path, align: 'center', highlight: true })

// 2. 编辑保存后：局部增删 + 定位，一步到位
await locator.applyMove({ data, oldParentId, newParentId, path, siblings })

// 3. 反向能力：包住一段会改变树结构的操作，结束后视口不动
await locator.keepViewport(fn, anchorKey)
```

`locate` 才是核心——**编辑后定位、搜索结果定位、URL 带 id 进来定位，本质是同一件事**，
`applyMove` 只是在它前面加了一段结构调整。演示页里那个「搜索定位」按钮和编辑保存
走的是同一个 `locate`。

### 返回值

不抛异常，失败都在返回值里，调用方按需给提示：

| reason | 含义 |
| --- | --- |
| `no-tree` | 树实例没了（组件已销毁） |
| `no-path` | 拿不到祖先链，且节点不在树上 |
| `path-broken` | 祖先链某一级不在 `nodesMap` 里（`at` 指出是哪一级），通常是并发修改 |
| `timeout` | 某一级 lazy load 超时（`at` 指出卡在哪） |
| `aborted` | 被后发起的定位取代，或调了 `cancel()` |
| `not-found` | 展开完成但目标不在列表里 |
| `no-scroller` | 没找到 RecycleScroller 容器 |

成功时返回 `{ ok: true, index }`；`applyMove` 还会多带一个 `orderUnknown`（见下）。
`index` 是节点在扁平列表里的下标，展示成"第几行"要 +1。

### applyMove 的参数

| 参数 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| `data` | ✅ | Object | 编辑后的完整节点数据，即后端返回的那个节点对象 |
| `key` | — | String/Number | 节点的 node-key 值。不传则取 `data[store.key]` |
| `oldParentId` | ✅ | String/Number/null | **打开弹窗那一刻**的父 id |
| `newParentId` | ✅ | String/Number/null | 保存后的父 id |
| `path` | 建议 | String/Array | 新位置的祖先链，格式见下一节 |
| `siblings` | 建议 | Array | 新父下的完整子级列表，用来保证同层顺序 |

三个容易错的点：

1. **`oldParentId` 必须在打开弹窗时就存下来**，不能在保存时从表单读——表单里的父级
   已经被用户改成新的了。这两个 id 一比较，决定走"就地改数据"的快路径还是完整流程。
2. **`data` 的字段结构要匹配树的 `:props`**。走 `append` 分支时它会直接成为新节点的
   `data`，缺了 `label`/`isLeaf` 对应的字段，节点会渲染成空白、或叶子判断错乱。
   后端字段名对不上就在传进来之前转换。
3. `newParentId` 传 `null` / `undefined` / `''` / `'0'`（`rootPlaceholders` 里配的）
   都识别为根级，下拉树清空后的 `undefined` 直接传即可，不用自己转。

若 `newParentId === oldParentId`（只改名没移动），内部走快路径：只
`Object.assign(node.data, data)`，不碰树结构，滚动位置与展开态零抖动，然后照常定位高亮。
这条路径不需要 `siblings`。

## 三、后端契约

### 祖先链 `ancestors`

**这是整套方案的地基。** 新上级可能在一个从未展开过的分支里，前端连 `nodesMap`
里都没有它，不知道要展开哪几级。

推荐直接把表里那列 materialized path 原样返回（若依的 `sys_dept.ancestors` 就是）：

```json
{ "id": "3301", "parentId": "33", "ancestors": "0,1,33" }
```

`tree-locator` 对格式很宽容，下面这些都收：

- 逗号串 `"0,1,33"`、斜杠串 `"0/1/33"`、数组 `["0","1","33"]`
- 含不含自身都行（含的话自动去掉末尾）
- 虚拟根 `'0'` 自动滤掉（`rootPlaceholders` 可配，你的树真有 id 为 0 的节点就传 `[]`）

**⚠️ 唯一的硬性要求是 id 类型。** 后端 `ancestors` 是字符串，`split` 出来全是 string；
而 `id` 字段在 JSON 里常常是 number。`nodesMap[key]` 走对象取值、数字字符串都能命中，
让人以为没问题；但最后 `dataList.findIndex(n => n.key === key)` 是严格相等，
类型不一致直接 -1——**症状是"展开全对了就是滚不过去"，不报错**。

模块内部会按 `dataList[0].key` 的实际类型自动对齐，但仍建议后端统一返回字符串
（`Long` 主键顺带配上 `ToStringSerializer`，避免雪花 ID 在 JS 里精度丢失）。

### 新上级的子级 `siblings`

`store.append` 只会把节点塞到**末尾**。同层如果按 `sort` 排序，不给 `siblings`
就会出现"看着在最后、刷新页面后跳到中间"的不一致。

格式就是「新父下那一层的完整子级数组」，和懒加载 `load` 里 resolve 的数据一模一样：

```json
{
  "node": { "id": "3301", "name": "杭州市", "parentId": "33", "leaf": true },
  "ancestors": "0,1,33",
  "siblings": [
    { "id": "3302", "name": "宁波市", "parentId": "33", "leaf": true },
    { "id": "3301", "name": "杭州市", "parentId": "33", "leaf": true },
    { "id": "3303", "name": "温州市", "parentId": "33", "leaf": true }
  ]
}
```

后端侧就是移动完之后再查一次：`where parent_id = #{newParentId} order by sort_num`。

三条要求：

1. **数组顺序即最终显示顺序**——`updateChildren` 的实现是「先把该层孩子全部 remove，
   再按数组顺序逐个 append」，前端不再排序。
2. **⚠️ 必须包含刚移动的那个节点自己。** 既然是清空重建，漏了它就等于把它从树上删了：
   保存成功、旧父没了、新父下也找不到，紧接着 `locate` 报 `not-found`。
   后端若是"先 update 再 select"天然包含；在事务里提前查的就要留意。
3. **每个元素的字段要匹配树的 `:props`**，且**不要带 `children`**——懒加载树靠展开时
   才拉下一层，元素里带子级会让这一层的节点状态错乱。

**不想改保存接口的话，`siblings` 可以由前端补**：保存成功后再调一次已有的「拉一层」
接口（就是懒加载在用的那个），代价是多一次请求，但零后端改动：

```js
const res = await updateNode({ id, name, parentId })
const siblings = await fetchChildren(res.node.parentId)   // 复用懒加载接口
await locator.applyMove({ data: res.node, ..., siblings })
```

**如果后端只能给插入位置 `index`**：模块目前只实现了 `siblings` 这条路，可以自己变通，
或者按需给 `applyMove` 加一个 `index` 分支（几行的事，尚未实现）：

```js
const parent = tree.store.nodesMap[newParentId]
const ref = parent.childNodes[index]
if (ref) tree.insertBefore(data, ref.data)
else tree.append(data, parent.data)
```

不给 `siblings` 不是错误，是降级：节点 append 到末尾，返回值 `orderUnknown: true`。
那一层本来就不排序的话，可以一直不给。

### 如果后端给不了

父级选择器是**树**的话，用户点选新父那一刻就能自己算：

```js
import { pathOfNode } from '@/utils/tree-locator'
const path = pathOfNode(pickedNode)   // 根在前、不含自身
```

两棵树是不同实例没关系，这里只取 `key`。但父级选择器如果是扁平下拉、
或支持**搜索选父级**，用户可能选中一个前端没加载过的节点，那就只能靠后端的 `ancestors`。

## 四、applyMove 的处理逻辑

```
新父 === 旧父？ → Object.assign(node.data, data) 就地改，不动树结构
                  （滚动位置、展开态、勾选态零抖动）
       ↓ 否
① tree.remove(oldData)              从旧父摘除
② 新父分四种情况：
     根级（null / undefined / '0'）→ append 到根，orderUnknown = true
     不在 nodesMap                  → 跳过，用户展开时自然拉到最新
     在但 !loaded                   → 跳过（append 会先显示一个孤零零的孩子，
                                       等真正展开时 loadData 又清空，白闪一下）
     已 loaded                      → 有 siblings 走 updateChildren
                                       否则 append + orderUnknown
③ locate(key, { path })
```

第 ② 步里 `updateChildren` 内部是「先 remove 所有孩子再逐个 append」，
会把那一层子孙的展开态一起抹掉，所以模块在它前后各做了一次展开态快照与恢复。

## 五、踩过的坑

### `node.expand(cb)` 可能永远不回调

`Node.loadData` 里有这么个判断：

```js
if (this.store.lazy === true && this.store.load && !this.loaded &&
    (!this.loading || Object.keys(defaultProps).length)) {
```

节点**正在 load** 时再调一次 `expand()`，整个分支被静默跳过，回调不执行——
`await new Promise(r => node.expand(r))` 直接挂死。

对策：先判 `node.loading` 走等待分支（轮询等 `loaded` 翻转），外层再加超时兜底。

### `store.remove` 会把 `currentNode` 置空

源码里显式写了。移动之后必须重新 `setCurrentKey`，否则高亮没有落点——
模块在 `locate` 末尾统一处理了。

### 高亮 class 要挂在树根，不能挂在行 DOM 上

虚拟滚动的行 DOM 是复用的。直接给某个 `.el-tree-node` 加 class，
用户一滚动，这个 DOM 就被拿去渲染别的数据了，**闪烁会串到无关的行上**。

所以 class 挂在树根（`ve-locating`），靠 `.is-current` 选中目标——语义跟着数据走：

```scss
.ve-locating .el-tree-node.is-current > .el-tree-node__content {
  animation: ve-locate-flash 1.5s ease-out;
}
```

同理，节点上"悬浮才出现的编辑按钮"必须用纯 CSS `:hover`，
用 JS 记 `hoverKey` 会因为 DOM 复用而串行。

### 定位要滚到视口中部，不是顶部

组件自带的 `scrollToItem(key)` 是滚到**顶部**，跨父级移动后这样跳过去很突兀。
模块用 `index * itemSize - (clientHeight - itemSize) / 2` 居中，
列表到底时浏览器会自动夹到最大可滚动值，目标行不居中但仍在视野内，属正常。

### 并发与销毁

递增 `seq` 作废上一次未完成的定位（用户连点、或定位途中又发起新的），
每一步都重新取树实例并检查——lazy load 是异步的，等回来时组件可能已经销毁了。
页面 `beforeDestroy` 里调一次 `locator.cancel()`。

## 六、拷到其他工程

`tree-locator.js` 不依赖本项目任何东西，直接拷过去即可。样式两种用法：

```scss
// 覆盖变量后再 import
$ve-locate-flash-color: rgba(64, 158, 255, 0.35);
@import '~@/utils/tree-locator.scss';
```

注意样式**不能放在 scoped 里**——规则要作用到树组件内部的 `.el-tree-node`，
scoped 的属性选择器打不进去。用非 scoped 块 + 页面级 class 前缀限定影响范围。

依赖的组件内部实现（升级 vue-easy-tree 时复核这几个）：

```
tree.store.nodesMap / tree.store.key / tree.dataList / tree.itemSize / tree.height
tree.remove() / tree.append() / tree.setCurrentKey() / store.updateChildren()
node.expand(cb) / node.loadData() / node.shouldLoadData() / node.loaded / node.loading
```

`src/utils/__tests__/tree-locator.spec.js` 用假树替身覆盖了路径归一化、
三级兜底、lazy 等待与超时、`applyMove` 四个分支、并发作废、视口还原——
拷过去一起带上，升级时先跑它。
